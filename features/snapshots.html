Snapshots

Fork feature

Snapshots are an addition in this fork. Neither the snapshots config block nor the internal/snapshot package exist upstream. See What this fork adds.

At every top-level user message, Crush captures the state of the project directory into a private git object store and ties it to the session and message that produced it. You can list the checkpoints of a session, diff any two, and restore the filesystem to any of them.

It is the filesystem counterpart of the conversation checkpoints used by context compaction: compaction checkpoints preserve the conversation, snapshots preserve the files.

How it works​

  • The store lives under <project>/.crush/git — a real git object database, but fully private. Your project's own .git is never read or written by the snapshot system.
  • Every capture walks the working tree, skipping .git, .crush, the project's .gitignore rules, and the configured exclusions. Content is stored content-addressed, so an unchanged file costs nothing on the next snapshot — when a snapshot's tree is identical to the previous one, the commit is reused entirely and no new objects are written.
  • Each snapshot is pinned with a refs/snapshots/{session}/{message} ref, so a session's history is addressable per message.
  • Capture happens in the background after the user message is persisted; a slow or failed snapshot never delays or breaks the turn.
  • Snapshots are taken only in git repositories (the home directory is explicitly excluded) and only for top-level sessions — sub-agents and steering messages never trigger one.

Browsing and restoring​

The Snapshots palette entry lists the session's snapshots newest first. enter restores the selected snapshot: the current tree is captured first — as a snapshot named "Before restore of …" — so a restore can itself be undone by restoring that capture. d copies the snapshot's diff against the previous one to the clipboard.

Restoring writes the snapshot's tracked files back into the working tree. Files that were never part of the snapshot are left untouched, so untracked work always survives a restore.

Configuration​

{
  "snapshots": {
    "enabled": true,
    "exclude": ["node_modules", "vendor", "dist", "build"],
    "keep": 0
  }
}
KeyDefaultDoes
enabledtrueCapture a snapshot at each user message. false disables the feature entirely.
excludenode_modules, vendor, dist, buildGlob or prefix patterns skipped during the snapshot walk (on top of .gitignore and .crush).
keep0 (unlimited)How many snapshots a session retains: the oldest beyond the newest keep are pruned after each capture.

Or from a crushrc file:

option snapshots-enabled true
option snapshots-exclude dist
option snapshots-exclude target
option snapshots-keep 50

Storage​

Snapshots live in the project database (snapshots table) alongside the git object store. Each row chains to the session's previous snapshot, so parent_snapshot_id forms a per-session history. Session deletion removes the rows; pruning of old git refs is available on the store (PruneKeep).
